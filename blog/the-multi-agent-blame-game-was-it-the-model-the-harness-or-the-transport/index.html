The Multi-Agent Blame Game: Was It the Model, the Harness, or the Transport?

Tracing three real failures — model, harness, transport — across four multi-agent builds.

The last installment in this series drew a line between having agent components and being agentic, and promised a closer look at what happens once you're coordinating more than one. This is that installment, and it comes from four crews I've built across four different frameworks and protocols: a six-agent PR reviewer on ChatDev, a PRD-writing crew on MetaGPT, a customer-service call-analysis crew on CrewAI, and a songwriting-and-critique crew pairing BeeAI and crewAI agents over ACP. Same shape every time: multiple agents, a coordinator, shared state. But the clearest paper trail is the PR review crew — I documented it closely enough at the time to reconstruct exactly what broke, and that's where the rest of this piece comes from.

The pattern goes back further, actually. My first-ever ChatDev run, building an IBM tutorial a year earlier, failed the same way three times before I traced it to a bad default token budget. That one turned into a full model-backend rebuild — its own story in itself.

Frameworks give you agent roles and orchestration primitives. Nothing tells you why a handoff actually produced garbage. Was the model reasoning badly? Did the harness pass stale or wrong context between agents? Was it a timing issue — one agent acting on state another hadn't finished writing? Everyone ships orchestration. Attribution is the part you still have to go looking for.

Three incidents from the PR review crew make the shape of the problem concrete, and in each case the framework told me nothing about which layer to look at. The crew splits the work across six agents — among them a Comment Poster, whose one job is taking a finished review and posting it back to the PR as a GitHub comment.

The harness didn't know when to stop. The Comment Poster agent called post_review_comment 43 times in a single run. ChatDev's engine has an implicit self-loop — it keeps calling the model until it responds with no tool call — and nothing in that loop told the model a successful call meant it was done. That's load-bearing engine behavior, and it's not in the docs or the YAML schema. The fix went into the prompt: "If the conversation already contains a result from post_review_comment... the tool has already succeeded. Do NOT call it again for any reason." Nothing in the base engine recognized that a successful tool call was already complete work and prevented the model from requesting it again — you have to tell it not to, explicitly, every time.

The model was fine, until it wasn't. One of the review agents came back empty on a reasoning model — no error, no crash, just nothing. Its reasoning tokens had eaten 1,198 of a 1,200-token generation budget. Same prompt, different runs, the reasoning-token usage ranged from about 1,100 tokens up to the full ceiling. There was no bug in my harness to find. The model's reasoning behavior varied between runs in a way I couldn't see from the final response, until I found the reasoning_effort parameter — instead of giving the model a bigger budget and hoping it finished in time, I could tell it directly to reason less.

And sometimes it's neither. The Comment Poster's tool result echoed the full review body back into context — 4,000 characters, duplicated, once in the original input and once in the tool result. That pushed the next request past what the provider would accept, and the API returned a 413: request too large. Nothing wrong with the reasoning, nothing wrong with the prompt. Just a transport-layer ceiling I hit because of how much text was moving between agents.

Three failures, three layers, and the same lesson each time: the framework will tell you something went wrong. It won't tell you where.

When a crew breaks now, this is what I actually check:

Harness — did the orchestration know the job was done? Or is it still calling a tool that already succeeded.

Model — did it have the budget to finish reasoning? Or did it spend that budget somewhere you can't see and come back empty.

Transport — did the payload actually fit through the boundary between agents? Or did something get duplicated, echoed, or bloated on the way across.

None of this is specific to ChatDev, and it's not a ranking of frameworks. LangGraph has a reported issue for the same tool-loop pattern — an agent looping until it hits the recursion limit — closed as not planned, with the existing recursion_limit parameter treated as the answer rather than something to fix. Recent research on infinite agentic loops treats it as a property of LLM agents generally, not one framework's flaw. Not evidence that the pattern is unique to ChatDev, but a pretty good indication it's common enough that a major framework's own maintainers consider it expected behavior, not a bug to chase.

None of these three failures showed up in any framework's error message as "harness bug," "model behavior," or "rate limit." They showed up as "the crew didn't work," and figuring out why meant reading a replay log, staring at a token count, and eventually finding a parameter buried in provider docs. That's the actual cost of multi-agent fragility — not that these systems break, but that nothing in them points you toward why.

If you're building or evaluating one of these systems, the practical version of this isn't "pick a mature framework" — mature frameworks have the same failure modes, they just turn some of them into a named parameter instead of a mystery. It's knowing the three shapes going in: an orchestration layer that doesn't know when to stop, a model quietly spending its own budget on thinking you can't see, and a payload that's grown past what the transport layer will carry. None of those show up in a demo. All three show up the first time you run something for real.

That's also the honest line between a portfolio project and a production system — not whether it works in the demo, but whether you've gone looking for these failure modes before they find you.
